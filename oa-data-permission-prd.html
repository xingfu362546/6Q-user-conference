1核心原则

经需求对齐后确认的设计基线

方案 A 权限跟 OA 组织树 + 组织类型，虎鲸补充项目维度
区域为核心 以「区域」组织类型为主要数据筛选依据；部门下可嵌套区域子组织
公司不参与 集团 → 部门/区域 有效；公司层不做数据过滤
取最宽（并集） 多组织挂靠、组织+项目双维度均取并集
只读 现阶段仅控制数据可见范围，不区分增删改
全业务覆盖 OA 下所有业务数据统一走此逻辑，需改造数据权限菜单
部门类型组织

组织类型说明

组织类型是否互斥在组织树中的角色数据权限影响
部门 与区域不互斥 容器型组织，可下设区域子组织（如地区发展部） 直接挂靠部门节点 → 可见全部；挂靠其下区域子组织 → 按区域规则
区域 与部门不互斥 运营中心、办事处等，承载地区数据边界 核心筛选依据：按地区匹配规则过滤
公司 — OA 层级节点 不参与数据过滤

6权限合并与判定流程

组织维度 ∪ 项目维度，多身份取最宽

// 最终可见数据集 可见数据 = ORG_SCOPE(用户) ∪ PROJECT_SCOPE(用户) ORG_SCOPE: 多组织挂靠时内部取最宽 含部门直连挂靠 → ALL 仅区域挂靠 → { data | region_match(user, data.region) } PROJECT_SCOPE: { data | data.project ∈ user.projects_from_虎鲸 }

实体关键字段用途
业务数据 region_code, project_code 权限分发的两个核心过滤属性
地区映射 ops_center_code ↔ office_code 运营中心下辖办事处推导
用户组织 org_type, region_code OA 同步，判定组织维度范围
用户项目 project_code 虎鲸同步，判定项目维度范围

8典型场景对照

组织维度与项目维度交叉时的最终可见范围

用户身份 组织维度 项目维度（虎鲸） 最终可见
地区发展部（部门直连） 全部 — 全部
地区发展部下 · 运营中心 A A 辖区 — A 辖区数据
办事处 X 仅 X — X 数据
办事处 X + 一阶项目成员 仅 X 全部一阶 X 数据 ∪ 全国一阶
运营中心 A + 二阶项目成员 A 辖区 全部二阶 A 辖区 ∪ 全国二阶
部门兼岗 + 办事处区域兼岗 全部（取最宽） — 全部
运营中心 A（非一阶辖区） A 辖区 一阶项目成员 A 辖区 ∪ 全国一阶

10已确认事项

需求评审结论记录

#议题结论
1项目权限与组织权限合并方式并集（取最宽），一阶成员可看全国一阶数据
2地区发展部定位部门类型，下可嵌区域子组织；以区域类型为核心区分数据可见性
3非办事处全职员工兼岗部门+区域兼岗时取最宽，确认可行
4部门与区域类型不互斥，用户可有多种组织挂靠
5运营中心隔离五大运营中心互不可见
6公司层级不参与数据过滤
7操作权限仅只读，不区分增删改
8适用范围OA 下全部业务数据
9地区映射OA 已维护，按员工办事处/区域匹配数据地区
10项目维护虎鲸系统维护项目成员，支持一阶/二阶/三阶等
