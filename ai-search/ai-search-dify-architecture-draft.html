AI 超级搜索 × Dify 方案

期数 HTTP + SSE；首次提交由 BFF/Dify 定 Tab；切 Tab只刷类目；同一 sessionId 多轮由 LLM 读上下文；仅在新关键词提交时清空 AI 对话。

← 交互原型（统一版）  ·  全部 Tab 瀑布参考页

已确认决策（v4）
  • ① 期数：直接 HTTP；LLM 只抽参，不编造期数。
  • ② 响应：SSE 流式 + cards；event:route 定 Tab。
  • ③ 知识库：课程/期数不进库；亮点来自 API。
  • ④ 意图收敛：首次搜索仅两类落地 —— ai_course_*（4 类合并路由）→ AI智搜；general_search → 全部 Tab。ai_unsupported 仅在「已在 AI 对话内」且垂类/闲聊时出现。
  • ⑤ Tab 切换：只按搜索框 keyword 请求对应类目 API，不走意图路由、不清 AI 历史。
  • ⑥ 对话保留：除非用户提交与上轮不同的新关键词（顶部搜索/回车），否则 APP 不得清空 AI 聊天；续聊、切 Tab 返回 AI 均保留。
  • ⑦ 多轮：BFF 固定 sessionId 调 Dify；节点 1/2 传入 history[]，由 LLM 结合上下文理解「还有吗」「南宁站」等，不靠前端 includes 猜。

2.1 抽象词 / 歧义词穷举（须写入 Dify Prompt + BFF 兜底）

下列词语不能单独作为「进 AI 智搜」的依据；须结合 history、完整句、或是否出现课名/城市/期数/报读动作。单独出现时默认 general_search → 全部 Tab。

类别词表（示例，可扩展）单独出现时的默认结合上下文可升级为
品牌/缩写 6Q、EQ、六Q、领袖营、高EQ general_search 带课名/期数/报读 → ai_course_*
阶别/模糊课级 一阶、二阶、三阶、初阶、进阶、工作坊 general_search +「智慧父母/高EQ/课名」或 history 已有 course → AI
泛化教育词 课程、课、上课、学习、培训、教育 general_search + 城市/开课/期数/导师 → phase_query 等
指代/续聊（无新实体） 还有吗、还有名额吗、这个、那个、换一个、继续 不视为新搜索 同 sessionId → enroll_action / 继承 slots
时间/范围模糊 最近、近期、什么时候、哪些、有没有、几点 general_search + 城市/开课 → phase_query
礼貌/指令壳 帮我、查一下、搜索、看看、推荐 剥离后按剩余实体判 —

泛主题 恋爱、咨询、亲子、沟通、情绪 general_search 精确课名命中 → course_by_name
站点/地名（无课名） 广州、南宁、深圳、站（单独） general_search history 有课 +「南宁站还有吗」→ enroll_action

3. LLM 如何设定「HTTP 请求用关键信息」（解决慢接口 + 防幻觉）

3.1 节点1：结构化抽参（强制 JSON Schema）

在 Dify 用 LLM 节点 + JSON Schema 输出（或「参数提取」），禁止此节点调用 HTTP。Prompt 核心：

  • 输入必含：session_id（与 APP/BFF 一致）、query、history[]（role/content）、anchor_query（本轮搜索锚定词，用于判断是否新话题）。
  • 续聊句（还有吗、这个站）必须读 history 继承 course_id / city，不得因单独命中「站」「吗」判成 general_search。
  • 单独抽象词（§2.1）→ general_search 或低置信 + 要求用户补充。
  • 城市标准名；课名可 raw 交 BFF 模糊匹配。

  "session_id": "sess_8f3a…",
  "intent": "enroll_action",
  "is_new_topic": false,
  "slots": {
    "keyword": "南宁站还有吗",

3.4 接口慢时的编排（推荐）

sequenceDiagram
  participant APP
  participant BFF
  participant Dify
  participant API as 期数API

  APP->>BFF: POST /search SSE
sessionId + query + history
  BFF->>Dify: 节点1 抽参 JSON（快，<1s）
同一 sessionId
  par 并行
    BFF->>API: 期数查询（可能慢）
    BFF->>Dify: 节点2 流式导语（仅 API 已返回的课名/城市，禁止列期号）
  end
  API-->>BFF: sessions[]
  BFF-->>APP: event:cards JSON
  BFF-->>APP: event:done
  • 超时（如 3s）：先 SSE 推送「正在查询期数…」+ 骨架卡；API 返回后再 event:cards 替换。
  • 缓存：同 city+course_id+日 短缓存 1–5 分钟，减轻重复慢查询。
  • 节点2 Prompt：明确写「期数列表以 cards 为准，你只写概括语」。

4.1 全部 Tab 聚合（BFF 建议）

GET /api/v1/search/all?q= 或 BFF 内并行：sessions（可选）、online-courses、mall、articles、videos、audios，每区返回 1–3 条 + 总数，与原型 ai-search-v1.html 瀑布区块一致。

AI 智搜不在对话流内拼接商城/文章/视频/音频卡片（图 4–8 仅出现在全部或垂类 Tab）。

5. 知识库策略（按你的结论）

课程/期数/价格/名额 → 一律不进知识库，全部实时 HTTP。

若未来需要，仅可考虑极静态内容单独库：APP 使用说明、报读规则总则（且接受低频手工更新）。与课程 SKU 无关。

课程「亮点介绍」：来自 GET /courses/{id} 的 highlight 字段注入节点2，而非 RAG。
