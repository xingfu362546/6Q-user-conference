# 标签规则 · 产品优化方案

> 视角：用户画像 / CDP 标签系统资深产品经理  
> 基于当前原型（属性 / 事件 / 浏览页面 + 且或嵌套）与业务访谈结论

---

## 一、规则在系统中的位置

标签规则本质是 **「用户圈选 DSL」**：用可执行的布尔表达式，从统一用户 ID 空间中筛出一批人，再写入标签结果表。

```mermaid
flowchart LR
  A[数据源绑定] --> B[规则编译]
  B --> C[离线/实时计算]
  C --> D[版本快照]
  D --> E[覆盖人数 / 执行历史]
```

运营真正关心的是：**谁会被圈进来、规则是否写对、算完后多少人**。规则编辑器的一切优化都应服务于这三点。

---

## 二、三类条件的本质（不要混用语义）

| 类型 | 回答的问题 | 时间是否必需 | 典型错误 |
|------|------------|--------------|----------|
| **用户属性** | 用户「是谁 / 当前状态」 | 仅当字段为时间型 | 把「注册渠道」写成事件 |
| **行为事件** | 用户「做过什么」 | **必需**（默认最近 7/30 天） | 只写「发生过」不写时间范围 |
| **页面行为** | 用户「看过哪、停留多久」 | **必需** | 路径 + 时长 + 日期三套控件堆在一行 |

**建议命名（面向运营）：**

- 用户属性（原「属性」）
- 行为事件（原「事件」）
- 页面行为（原「浏览页面」）— 仍是行为子类，但用页面专用模板降低配置成本

页面行为不要与事件平级到「三种世界观」，对外可说 **两大类：画像属性 + 行为（含页面）**，避免运营理解成三套独立系统。

---

## 三、当前设计的主要问题

### 1. 时间维度不统一（P0）

- 页面行有「最近 N 天 / 固定区间」，事件行却没有显式时间窗口。
- 属性里的「注册时间早于」与页面「浏览时间」控件形态不一致。

**后果：** 运营写出 **无时间边界** 的事件规则 → 全量扫描、任务超时（与执行历史失败样例一致）。

### 2. 事件配置顺序不符合心智（P0）

当前：`点击事件 → 发生过 → 社区转发 → 总次数`

运营心智：`最近 30 天内 → 做过 → 社区转发 → 至少 1 次`

**应改为固定句式模板**，字段顺序与口语一致。

### 3. 缺少「规则可读性」层（P0）

只有下拉框，没有 **自然语言摘要**。复杂且/或嵌套时，运营无法自检，评审只能靠研发读 SQL。

### 4. 嵌套组使用边界不清（P1）

有且/或切换，但未说明：

- 何时用嵌套（组内或、组间且）
- 嵌套层级上限
- 与扁平多条条件的等价关系

**建议：** 嵌套默认折叠；提供 **「添加条件组」** 而非「添加嵌套」；组标题显示「满足以下任一条件」。

### 5. 页面行为一行控件过多（P1）

路径 + 匹配方式 + 时长类型 + 比较符 + 秒数 + 日期区间混排，认知负荷高。

**建议拆为两步：**

1. 页面是谁（路径/名称 + 匹配）
2. 行为约束（在何时 + 停留/访问次数）

### 6. 否定条件缺失（P1）

画像常见需求：**最近 N 天未做过某事件 / 未访问某页**。仅「发生过」不够。

### 7. 保存前无「试算」（P1）

已有「保存并计算」，但缺少 **保存前预估人数**。误配置要等整批任务失败才知道。

### 8. 与标签数据类型的关系未暴露（P2）

列表有布尔/枚举等类型，规则页未说明 **标签输出类型** 由规则决定还是人工选择（影响下游投放系统）。

## 四、推荐的信息架构（优化后）

```
标签规则
├── [规则解读] 自然语言摘要（实时）
├── [预估覆盖] 试算人数（不保存）
├── 条件组（顶层 且/或）
│   ├── 条件 1：用户属性 | ...
│   ├── 条件 2：行为事件 | 时间范围 | 做过/未做 | 事件 | 聚合
│   ├── 条件 3：页面行为 | 页面 | 行为指标 | 时间范围
│   └── [+ 添加条件]  [+ 添加条件组]
└── 校验提示（缺时间范围、矛盾条件等）
```

## 五、分优先级改进清单

### P0（一期必做）

| 编号 | 改进 | 说明 |
|------|------|------|
| R1 | **统一时间组件** | 行为/页面必选：最近 N 天 / 固定区间 / 自某日以来；默认最近 30 天 |
| R2 | **事件句式模板** | `[时间] + [做过/未做过] + [事件名] + [次数/天数聚合]` |
| R3 | **规则解读条** | 顶部实时生成可读句子，支持展开查看完整逻辑树 |
| R4 | **保存前校验** | 无时间范围、空值、互斥条件 → 阻断保存并计算 |
| R5 | **行为默认时间** | 新建事件/页面条件时自动带「最近 7 天」，减少漏配 |

### P1（一期尽量 / 紧接迭代）

| 编号 | 改进 | 说明 |
|------|------|------|
| R6 | **预估人数** | 异步试算，显示约 N 人 + 上次成功版本对比 |
| R7 | **未做过** | 事件、页面均支持否定 |
| R8 | **条件组文案** | 「满足以下全部/任一」替代裸且/或 |
| R9 | **页面两步向导** | 先选页面，再选时间与指标 |
| R10 | **复制规则差异提示** | 复制后高亮「请修改名称」+ 可选对比源标签 |

### P2（二期）

| 编号 | 改进 | 说明 |
|------|------|------|
| R11 | 规则模板库 | 高价值亲子/活跃/流失等一键套用 |
| R12 | 规则版本对比 | 改规则前后覆盖 Diff |
| R13 | 序列行为 | 先 A 后 B  within N 天 |
| R14 | 标签输出类型 | 与规则联动或显式选择 |

## 六、三类条件的推荐配置字段

### 用户属性

| 字段 | 说明 |
|------|------|
| 属性字段 | 来自数据源字典，分组展示 |
| 运算符 | 等于 / 不等于 / 包含 / 大于 / 早于 / 晚于 …（随字段类型变） |
| 值 | 枚举下拉 / 自由输入 / 日期 |

**不需要**全局时间窗口（除时间型属性外）。

### 行为事件

| 顺序 | 字段 |
|------|------|
| 1 | 时间范围（必填，默认最近 30 天） |
| 2 | 做过 / 未做过 |
| 3 | 事件（可搜索） |
| 4 | 聚合：总次数 / 天数 / 分布 … |
| 5 | 比较符 + 阈值 |

### 页面行为

| 步骤 | 字段 |
|------|------|
| 页面 | 路径/名称 + 匹配方式 |
| 指标 | 访问次数 / 停留时长 / 末次访问时间 |
| 时间 | 与行为事件共用时间组件 |

## 七、与计算 / 列表的联动（避免产品断点）

1. **规则变更 ≠ 立即改覆盖人数**  
   列表人数仍是「上次成功版本」→ 规则页保存并计算后，应引导用户回列表看新任务状态。

2. **失败版本与规则**  
   执行历史失败时，规则页应可 **「查看当时规则快照」**（只读），避免运营改规则后无法复盘。

3. **数据源锁定**  
   合理：字段字典稳定。规则里字段下拉应 **仅展示已绑定数据源** 下的表字段，避免选到未接入字段。

---

## 八、一句话原则（给设计与研发）

> **让运营像说话一样配规则，让系统像编译器一样查错；时间范围是行为条件的空气，没有就憋死。**
